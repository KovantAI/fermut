# Security policy

## Supported versions

fermut is pre-1.0. Only the latest released `0.x` version receives
security fixes. Older versions are end-of-life the day the next release
ships.

| Version | Supported |
|---------|-----------|
| 0.x (latest) | ✓ |
| All other versions | ✗ |

## Reporting a vulnerability

**Do not open a public GitHub issue for security reports.** Instead, contact
the maintainers privately:

- **Email**: [security@kovant.com](mailto:security@kovant.com)
- **Subject prefix**: `[fermut security]`
- **Encryption**: PGP available on request.

Please include:

1. fermut version (`fermut --version`).
2. A minimal reproducer (the smallest input that triggers the issue).
3. Impact assessment — what an attacker could do.
4. Suggested fix or mitigation, if you have one.

## Response timeline

| Step | Target |
|------|--------|
| Acknowledgement of report | within 3 business days |
| Initial severity assessment | within 7 business days |
| Patch availability or status update | within 30 days |
| Coordinated public disclosure | within 90 days of initial report |

We will coordinate the disclosure date with you. If a fix takes longer than
90 days, we will explain why and propose a revised timeline.

## Scope

The following are in scope:

- **Sandbox escape from a mutant** — if a mutation generated by fermut
  can break out of the per-mutant temp-dir mirror and modify the original
  source tree, that's a security issue.
- **Arbitrary code execution from a config file** — `fermut.toml`
  parsing should not execute attacker-controlled code beyond what the
  documented schema implies.
- **Path traversal through `--tests`, `--cache-path`, `--json`, etc.** —
  fermut should not write outside the directories the user provides.
- **Information disclosure through reports** — JSON/HTML reports
  shouldn't leak filesystem contents beyond what the user's source tree
  intentionally exposes.

Out of scope:

- A mutant changing the behavior of the user's program. That's the whole
  point — not a vulnerability.
- A user passing `--pytest-arg "rm -rf /"`. fermut forwards args
  verbatim; controlling pytest invocation is the user's responsibility.
- Issues in `pytest`, `ty`, `ruff`, `python`, or the user's own code.
  Report those upstream.

## Cache integrity in CI

`fermut` keeps a per-mutant result cache at `.fermut/cache.json`. When the
cache is restored from a shared artifact store between CI jobs — common
for caching warm runs across PRs — a malicious commit could pre-seed
entries to mark real survivors as `Killed`, inflating the score.

To defend against this, set `FERMUT_CACHE_KEY` to a CI-secret value:

- When set, every cache entry is signed with HMAC-SHA256 on insert and
  verified on load. Entries with a missing or mismatching MAC are
  dropped (with a warning).
- When unset, the cache behaves as it always has — no signing, no
  verification. Local-dev workflows that don't share cache between
  untrusted contributors don't need to opt in.
- Pick a value with at least 128 bits of entropy and store it as a
  pipeline secret. Rotate it to invalidate the cache after an incident.

This is integrity, not confidentiality: outcomes are still readable on
disk. The MAC just prevents an attacker without the key from forging
entries that lookups will trust.

## Untrusted repositories

`fermut` walks ancestors of the source path looking for `fermut.toml` (or
`[tool.fermut]` in `pyproject.toml`). If you `git clone` an unfamiliar
repository and run `fermut` inside it, the project's committed config
governs the run.

The config cannot execute code directly — it's TOML, not Python — but it
can redirect:

- `tests_path` (where the mutation runner invokes pytest)
- `pytest_args` (verbatim args forwarded to pytest)
- `cache_path` / `history_path` (where state is written)

This is the same trust posture as running `make`, `npm install`, or
`pip install -e .` in someone else's repo: review before you run.

Mitigations:

- The discovered config path is logged at `info` level on every load.
  When in doubt, scan `fermut run -v ...` output for `config: loaded`.
- Set `FERMUT_NO_CONFIG=1` to skip discovery entirely and use defaults +
  explicit CLI flags only.

`fermut suggest --apply` refuses to write through a symlink at the
generated test's target path. A hostile contributor cannot land a
symlink under `tests/` that redirects the write outside the project.

## LLM features — data egress

`fermut suggest`, `fermut explain --llm`, and `--equiv-llm` send portions
of your source code (the surrounding context of each mutated line, the
enclosing symbol, and optional sample tests) to the configured LLM
provider — by default Anthropic's Messages API.

What this means in practice:

- Anything visible in those snippets — including hard-coded secrets in
  test fixtures, customer data baked into source, or proprietary
  algorithms — is transmitted to a third party.
- fermut applies a best-effort redaction pass to common secret shapes
  (Anthropic / OpenAI / GitHub / AWS / Slack / Google keys, JWTs, long
  hex tokens, and `password=`/`token=`/`api_key=`-style assignments)
  before sending. Redaction is **not** a guarantee; novel key formats
  or context-dependent secrets will get through.
- Disable LLM features (`--no-llm` flags, or simply don't pass
  `--equiv-llm`/`suggest`/`explain --llm`) if your source tree contains
  data that must not leave the host.
- API keys (`ANTHROPIC_API_KEY` / `FERMUT_ANTHROPIC_API_KEY`) are read
  from the environment and never logged or persisted to the cache.
